Einstieg

Stell dir einen Techniker vor, der eine entfernte Werkshalle steuert, indem er seine Kommandos auf Postkarten schreibt und per Post verschickt – inklusive des Passworts für den Zugang zur Halle. Jeder Postbote auf dem Transportweg kann mitlesen, was dort steht, und die Postkarte sogar unbemerkt austauschen. Genau so funktionierte früher Telnet: Kommandos und Zugangsdaten wanderten unverschlüsselt im Klartext über das Netzwerk. SSH (Secure Shell) ist wie ein verschlossener, versiegelter Kurierumschlag für dieselben Fernsteuerungs-Kommandos: Niemand auf dem Transportweg kann mitlesen oder die Nachricht unbemerkt verändern.

Konzept

SSH (Secure Shell) ist ein verschlüsseltes Protokoll für den Fernzugriff auf Systeme, typischerweise um sich remote auf einer Kommandozeile (Shell) eines Servers anzumelden und dort zu administrieren. SSH läuft standardmäßig über TCP-Port 22 und ist die verschlüsselte Ablösung des veralteten Telnet (Port 23), das Kommandos und Zugangsdaten unverschlüsselt im Klartext überträgt und deshalb als unsicher gilt.

Authentifizierung: Passwort vs. Public-Key

SSH unterstützt zwei Authentifizierungsverfahren:

VerfahrenFunktionsweise
Passwort-Authentifizierung Benutzername und Passwort werden über die verschlüsselte SSH-Verbindung übertragen und auf dem Server geprüft – anfällig für Brute-Force-Angriffe auf schwache Passwörter
Public-Key-Authentifizierung Ein Schlüsselpaar aus privatem und öffentlichem Schlüssel wird genutzt: Der private Schlüssel bleibt auf dem Client, nur der öffentliche Schlüssel liegt auf dem Server (in der Datei authorized_keys). Es wird dabei kein Passwort über das Netzwerk übertragen, was diese Methode als sicherer gilt

Neben der interaktiven Shell wird SSH auch als sicherer Transport für Dateiübertragung genutzt: SCP (Secure Copy) kopiert einzelne Dateien, SFTP (SSH File Transfer Protocol) bietet einen vollwertigen, verschlüsselten Dateizugriff mit Verzeichnisnavigation – beide bauen auf derselben SSH-Verbindung auf.

Abgrenzung zu TLS

SSH ist ein eigenständiges Protokoll speziell für Fernzugriff, Terminal-Sitzungen und Dateitransfer (SCP/SFTP). TLS dagegen sichert primär Anwendungsprotokolle wie HTTP (als HTTPS) ab und arbeitet mit einer eigenen Zertifikatsprüfung über Zertifizierungsstellen. Details zu Zertifikaten und PKI stehen in der Einheit Zertifikate, PKI & TLS – SSH benötigt dafür keine CA, sondern verlässt sich auf einzeln hinterlegte Schlüssel bzw. beim ersten Verbindungsaufbau auf einen sogenannten Fingerprint-Abgleich.

Praxisbeispiel

Ein Systemadministrator muss einen entfernten Linux-Server in einem anderen Rechenzentrum administrieren.

  • Er verbindet sich per SSH auf Port 22 mit dem Server und meldet sich per Public-Key-Authentifizierung an – sein privater Schlüssel bleibt dabei auf seinem eigenen Notebook, nur der öffentliche Schlüssel liegt auf dem Server.
  • Über die verschlüsselte SSH-Sitzung startet er einen hängengebliebenen Dienst neu und prüft die Log-Dateien direkt auf der Kommandozeile.
  • Eine Konfigurationsdatei lädt er anschließend per SFTP auf seinen Rechner herunter, um sie lokal zu bearbeiten.
  • Da der Server bislang noch zusätzlich per Telnet erreichbar war, deaktiviert er diesen Zugang, da er Zugangsdaten unverschlüsselt überträgt.

Merksatz

SSH ist ein verschlüsseltes Protokoll für Fernzugriff über TCP-Port 22 und löst das unverschlüsselte Telnet ab. Authentifizierung per Passwort oder per sichererem Public-Key-Verfahren (privater Schlüssel bleibt beim Client). SCP und SFTP nutzen SSH für verschlüsselten Dateitransfer. Anders als TLS, das Anwendungsprotokolle wie HTTPS absichert, ist SSH ein eigenständiges Protokoll für Terminal-Zugriff und Dateitransfer.
