An der zentralen Datenbank arbeiten drei Leute. Die Auszubildende hat Modell, Sichten und API-Entwurf erstellt und schreibt das Importskript, ein Kollege baut die Auswertungen, eine Kollegin im Homeoffice programmiert die Web-API. Alle ändern Dateien im selben Projekt. Ohne Ordnung überschreibt bald jemand die Arbeit eines anderen, und niemand weiß mehr, welcher Stand läuft. Eine Versionsverwaltung verhindert das.

Was eine Versionsverwaltung leistet

  • Sie speichert jeden Stand eines Projekts mit Datum, Autor und Beschreibung.
  • Jede Änderung lässt sich nachvollziehen und ein älterer Stand wiederherstellen.
  • Mehrere Personen arbeiten parallel und führen ihre Änderungen kontrolliert zusammen.

Das verbreitetste Werkzeug ist Git. Git ist verteilt: Jede Person hat eine vollständige Kopie des Projekts mit seiner ganzen Geschichte, das Repository. Ein gemeinsames Repository auf einem Server dient als Treffpunkt, über den alle ihre Stände austauschen. Auch Commits gehen ohne Verbindung; nur zum Austausch (pull, push) braucht man den Server.

Die wichtigsten Befehle

BefehlWirkung
git clone <adresse>gemeinsames Repository auf den eigenen Rechner kopieren
git statuszeigt geänderte und neue Dateien
git add <datei>Änderung für den nächsten Stand vormerken
git commit -m "…"vorgemerkte Änderungen als neuen Stand (Commit) mit Beschreibung speichern
git logListe der bisherigen Commits
git pullneue Commits der anderen vom Server holen und einarbeiten
git pusheigene Commits auf den Server übertragen

Ein Commit fasst eine zusammengehörige Änderung zusammen, etwa „Import: Tierarten über Zuordnungstabelle vereinheitlichen“. Die Beschreibung sagt, was und warum geändert wurde. Kleine, häufige Commits sind leichter zu prüfen und bei Bedarf zurückzunehmen als ein großer am Ende der Woche.

Branches: parallel entwickeln

Ein Branch (Zweig) ist eine eigene Entwicklungslinie. Der Hauptzweig, meist main, in älteren Repositories master, enthält den Stand, der läuft. Für eine neue Aufgabe legst du einen eigenen Branch an (git switch -c import-labor, ältere Form git checkout -b import-labor), arbeitest dort und führst ihn erst zurück (Merge), wenn die Aufgabe fertig und geprüft ist. Bis dahin stört deine halbfertige Arbeit niemanden.

Haben zwei Personen dieselbe Stelle einer Datei verschieden geändert, kann Git nicht selbst entscheiden. Es meldet einen Konflikt und markiert beide Fassungen in der Datei. Ein Mensch wählt die richtige Fassung oder kombiniert beide und schließt den Merge mit einem Commit ab.

Was nicht ins Repository gehört

Kennwörter, API-Schlüssel und echte Datenbestände gehören nicht ins Repository: Was einmal committet ist, bleibt in der Geschichte auffindbar, auch wenn die Datei später gelöscht wird. In der Datei .gitignore trägst du Dateien ein, die Git nie aufnehmen soll, etwa eine lokale Datei mit Zugangsdaten oder Exporte mit Kundendaten. .gitignore wirkt nur auf Dateien, die Git noch nicht aufgenommen hat. Ist ein Kennwort doch committet worden, gilt es als bekannt und wird sofort geändert.

Beispiel

Nach einer Änderung am Importskript fehlen seit dem Vormittag alle neuen Laborwerte. Mit git log findet die Auszubildende den Commit vom Vortag, „Labor-CSV: Trennzeichen auf Komma“. Das Labor liefert aber weiterhin Semikolon. Sie nimmt die Änderung mit einem neuen Commit zurück (git revert) und stellt ihn als Pull Request (Kapitel 8.5.2). Nach kurzer Prüfung wird er übernommen, und der nächste Lauf übernimmt die Werte wieder.

„Git ist dasselbe wie eine Datensicherung.“ Git verwaltet die Stände von Quelltext und Konfiguration, die bewusst committet wurden. Datenbanken, Nutzerdaten und alles, was nicht committet ist, sichert es nicht. Die Datensicherung bleibt nötig.

Git speichert jeden Stand als Commit mit Autor und Beschreibung. Branches trennen parallele Arbeit, pull und push gleichen mit dem Server ab, Zugangsdaten bleiben draußen.
