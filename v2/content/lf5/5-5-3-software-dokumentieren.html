Ein halbes Jahr nach der Einführung meldet die Praxis, dass bei einigen übernommenen Telefonnummern die Vorwahl fehlt. Wer das Importskript geschrieben hat, ist im Urlaub. Ob der Fehler schnell gefunden wird, hängt jetzt an der Dokumentation: Was sollte das Skript tun, wie ist es aufgebaut, was wurde wann geändert?

Wozu dokumentieren?

Dokumentation hält Wissen fest, das sonst nur in einzelnen Köpfen steckt. Sie macht Software bedienbar, wartbar und prüfbar: Anwender schlagen nach, wie sie eine Funktion bedienen; Kollegen können Fehler beheben und erweitern, ohne alles neu zu verstehen; Auftraggeber und Auftragnehmer können zeigen, was vereinbart und was geliefert wurde. Dokumentation entsteht am besten während der Arbeit, nicht erst am Projektende.

Kommentare im Code

Ein guter Kommentar erklärt, warum etwas so gelöst ist. Was passiert, sollte der Code selbst durch sprechende Namen zeigen.

// schlecht: wiederholt nur den Code
zaehler ← zaehler + 1    // zaehler um 1 erhöhen

// besser: begründet eine Entscheidung
// Altsystem speichert Nummern ohne Vorwahl;
// die Praxis liegt im Ortsnetz 0341, deshalb ergänzen
IF LENGTH(telefon) < 8 THEN
    telefon ← "0341" + telefon
END IF

Hier zählt LENGTH die Zeichen eines Textes, und + hängt zwei Texte aneinander.

Änderungen nachvollziehen

Software wird nach der Übergabe weiter geändert. Ein Änderungsprotokoll (Changelog) hält je Version fest, was neu ist, was geändert und was behoben wurde. Eine Versionsverwaltung wie Git speichert jeden Stand des Quellcodes mit Datum, Autor und einer kurzen Beschreibung. So lässt sich nachvollziehen, wann eine Zeile geändert wurde, und ein älterer Stand lässt sich wiederherstellen.

Modelle mit UML

Für die technische Dokumentation werden Abläufe und Strukturen oft grafisch dargestellt. Die UML (Unified Modeling Language) ist eine genormte Sammlung solcher Diagramme. Drei davon begegnen dir häufig:

  • Anwendungsfalldiagramm (Use-Case-Diagramm): Wer nutzt das System wofür? Etwa Empfang „Termin vergeben“, Tierärztin „Behandlung erfassen“.
  • Klassendiagramm: Aus welchen Klassen (Bauplänen für Objekte wie „Tier“) mit welchen Daten (Attributen) und Funktionen (Methoden) besteht die Software, und wie hängen sie zusammen?
  • Aktivitätsdiagramm: In welcher Reihenfolge laufen die Schritte eines Ablaufs, mit Verzweigungen?

Wie du diese drei Diagramme liest und zeichnest, folgt in Kapitel 5.5.4.

Beispiel

Zurück zu den Nummern ohne Vorwahl. Im Changelog steht bei Version 1.2: „Import: Nummern ohne Vorwahl werden um 0341 ergänzt.“ In der Versionsverwaltung findet die Kollegin die zugehörige Änderung, der Kommentar im Code erklärt die Regel. Damit ist die Ursache klar: Nummern mit Leerzeichen sind länger als 7 Zeichen und wurden deshalb nicht erkannt. Ohne diese Dokumentation hätte sie das Skript erst vollständig nachvollziehen müssen.

„Der Code ist die Dokumentation.“ Gut lesbarer Code ersetzt Kommentare an vielen Stellen, aber nicht die Benutzerdokumentation und nicht die Begründung, warum eine Anforderung so umgesetzt wurde.

Software wird für unterschiedliche Leser dokumentiert: Projektdokumentation für Auftraggeber und Team, Benutzerdokumentation für Anwender, Entwicklerdokumentation und Kommentare für alle, die die Software warten und ändern.
