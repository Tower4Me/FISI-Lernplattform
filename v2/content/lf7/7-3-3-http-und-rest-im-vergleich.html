Das alte Kühlaggregat wird ersetzt. Der Hersteller des neuen Modells bietet eine Schnittstelle an, über die man Status und Störungen abfragen kann, aber nicht per MQTT, sondern über das Web. Viele Geräte und Cloud-Dienste sprechen HTTP. Du musst einschätzen können, wann das passt und wann MQTT besser ist.

REST: Anfragen an Ressourcen

Bei einer REST-Schnittstelle (eine Web-Programmierschnittstelle, kurz Web-API) stellt ein Gerät oder Dienst seine Daten als Ressourcen unter Adressen bereit, etwa https://aggregat.lager.local/api/status. Ein Client fragt per HTTP an, der Server antwortet, meist mit JSON. Die HTTP-Methode sagt, was mit der Ressource geschehen soll:

MethodeBedeutungBeispiel
GETlesenaktuellen Status des Aggregats abfragen
POSTneu anlegen oder Aktion auslöseneine neue Alarmregel anlegen
PUTersetzen (Ressource vollständig neu setzen)Sollwert auf 3 °C setzen
DELETElöschenAlarmregel entfernen

Jede Anfrage steht für sich; der Server merkt sich zwischen zwei Anfragen nichts über den Client (zustandslos). Deshalb schickt der Client Zugangsdaten wie einen Schlüssel bei jeder Anfrage mit. Ob die Anfrage geklappt hat, zeigt der Statuscode: 200 bedeutet Erfolg, 401 fehlende oder ungültige Anmeldung, 404 Ressource nicht gefunden, 500 Fehler beim Server.

Anfrage oder Abonnement

Der wichtigste Unterschied zu MQTT: Bei HTTP fragt der Client, der Server antwortet (Anfrage und Antwort). Will die Auswertung wissen, ob sich etwas geändert hat, muss sie regelmäßig nachfragen (Polling). Bei MQTT schiebt der Broker neue Nachrichten von selbst zu den Abonnenten (Push).

HTTP/RESTMQTT
MusterAnfrage und Antwort zwischen zwei PartnernVeröffentlichen und Abonnieren über einen Broker
NeuigkeitenClient muss nachfragen (Polling)kommen sofort, sobald sie veröffentlicht werden
Aufwand je Nachrichtgrößer: jede Anfrage trägt vollständige Kopfzeilenklein: wenige Bytes Kopf auf einer bestehenden Verbindung
Verbreitungüberall im Web, in Cloud-Diensten, viele WerkzeugeStandard für Sensordaten und IoT-Plattformen
passt fürAbfragen bei Bedarf, Konfiguration, Anbindung an Webdiensteviele Geräte, häufige kleine Messwerte, Ereignisse

Beide schließen sich nicht aus. Häufig liefern Sensoren per MQTT, und eine Weboberfläche oder ein Cloud-Dienst liest die gesammelten Daten per REST ab.

Beispiel

Die Auswertung im Biomarkt fragt den Status des neuen Kühlaggregats jede Minute per GET über HTTPS ab und meldet sich dabei mit einem Zugangsschlüssel an. Meldet das Aggregat eine Störung, veröffentlicht die Auswertung sie unter biomarkt/kuehlraum/aggregat beim Broker. So landen alle Werte an einer Stelle, und Anzeige und Warnleuchte müssen nur MQTT verstehen.

„REST ist ein eigenes Protokoll wie MQTT.“ Nein: REST ist ein Architekturstil, der festlegt, wie man HTTP für Schnittstellen nutzt. Übertragen wird mit gewöhnlichem HTTP, verschlüsselt mit HTTPS.

  • REST: Ressourcen unter URLs, Methoden GET, POST, PUT, DELETE, Antwort meist JSON mit Statuscode; Client fragt, Server antwortet.
  • MQTT schiebt Neuigkeiten über den Broker zu den Abonnenten und eignet sich für viele kleine Messwerte; REST für Abfragen bei Bedarf und Webdienste.
