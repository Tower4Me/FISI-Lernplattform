Nicht alle Daten passen gut in Tabellen. Die Bestellungen des Futterlieferanten kommen als verschachteltes JSON mit wechselnden Feldern. Die Kühlschranksensoren liefern jede Minute einen Messwert. Für solche Fälle gibt es Datenbanken, die ohne feste Tabellen arbeiten. Sie heißen zusammengefasst NoSQL, heute meist als „not only SQL“ gedeutet.

Warum NoSQL

Relationale Datenbanken verlangen ein festes Schema und verteilen zusammengehörige Daten auf mehrere Tabellen. Das sichert Konsistenz, ist aber nicht immer passend:

  • Die Struktur der Daten ändert sich häufig oder ist von Datensatz zu Datensatz verschieden.
  • Es fallen sehr große Mengen an, die auf viele Server verteilt werden sollen (horizontale Skalierung).
  • Die Daten werden meist als Ganzes gelesen, etwa eine komplette Bestellung.

Vier Arten

Eine dokumentenorientierte Datenbank speichert jeden Datensatz als Dokument, meist in JSON oder einem verwandten Format. Ein Dokument kann verschachtelt sein, und Dokumente derselben Sammlung dürfen unterschiedliche Felder haben.

{ "bestellnr": "B-2025-0412",
  "standort": "Nord",
  "positionen": [
    { "artikel": "Nierendiät Katze 2 kg", "menge": 6 },
    { "artikel": "Welpenfutter 10 kg", "menge": 2 } ] }

Passt für: Bestellungen, Produktkataloge, Inhalte von Webseiten. Beispiel: MongoDB.

Ein Schlüssel-Wert-Speicher (Key-Value-Store) legt zu jedem eindeutigen Schlüssel einen Wert ab. Der Wert ist für die Datenbank meist nur ein Block; gesucht wird nur über den Schlüssel, das aber sehr schnell.

Passt für: Sitzungsdaten einer Webanwendung, Zwischenspeicher (Cache), Einstellungen. Beispiel: Redis.

Eine spaltenorientierte Datenbank (Wide-Column-Store) speichert Zeilen mit einem Schlüssel. Jede Zeile kann viele eigene Spalten haben, die zu Spaltenfamilien zusammengefasst sind, und die Daten lassen sich über viele Server verteilen.

Passt für: sehr große Datenmengen, viele Schreibvorgänge, etwa Messwerte vieler Sensoren über Jahre. Beispiel: Apache Cassandra.

Eine Graphdatenbank speichert Knoten (etwa Personen, Tiere, Praxen) und Kanten, die Beziehungen zwischen ihnen darstellen. Abfragen folgen den Kanten direkt, ohne Tabellen zu verknüpfen.

Passt für: stark vernetzte Daten, etwa soziale Netzwerke, Empfehlungen, Netzwerktopologien. Beispiel: Neo4j.

Relational oder NoSQL

Relationale DatenbankNoSQL-Datenbank
Strukturfestes Schema, Tabellenflexibel, je nach Art Dokumente, Schlüssel-Wert-Paare, Spalten oder Graphen
AbfrageSQL, genormtje nach Produkt eigene Abfragesprache oder Schnittstelle
KonsistenzTransaktionen mit ACID (Kapitel 8.3.5)oft lockerer: Änderungen sind erst nach kurzer Zeit überall sichtbar (letztendliche Konsistenz)
Wachstummeist durch einen stärkeren Servermeist durch mehr Server

Viele Betriebe nutzen beides nebeneinander. Die Grenzen verschwimmen: Relationale Systeme wie PostgreSQL können JSON speichern und abfragen, manche NoSQL-Systeme bieten Transaktionen.

Beispiel

Behandlungen, Tiere und Impfungen bleiben in der relationalen Datenbank: Sie hängen eng zusammen und müssen stimmen. Die Rohdaten der Kühlschranksensoren, jede Minute ein Wert über Jahre, legt das Systemhaus in einer spaltenorientierten NoSQL-Datenbank ab; für solche Messreihen gibt es auch eigene Zeitreihendatenbanken. In die zentrale Datenbank kommt nur eine Zusammenfassung je Tag.

„NoSQL heißt: keine Struktur und kein SQL.“ Die Daten haben sehr wohl eine Struktur, sie ist nur nicht für alle Datensätze vorgeschrieben. Manche NoSQL-Systeme verstehen sogar eine SQL-ähnliche Abfragesprache.

  • NoSQL-Arten: Dokument (verschachteltes JSON), Schlüssel-Wert (schneller Zugriff über Schlüssel), Spalten (riesige verteilte Mengen), Graph (vernetzte Beziehungen).
  • Relational bei festem Schema und strenger Konsistenz, NoSQL bei wechselnder Struktur, sehr großen Mengen und Verteilung auf viele Server.
