Ein Skript, das jede Nacht läuft, macht seine Fehler auch jede Nacht, und oft merkt es niemand. Deshalb prüfst du ein Skript, bevor es in den Betrieb geht: erst auf dem Papier, dann mit Testdaten. Den Schreibtischtest kennst du aus LF5, Kapitel 5.4.5; hier wendest du ihn auf ein Administrationsskript an.

Ein Skript mit Fehler

Das Skript soll aus der Plattenbelegung der vier Server (in Prozent) den höchsten Wert und die Zahl der Server über 80 % ermitteln:

belegung ← [92, 71, 65, 88]
max ← 0
anzahl ← 0
FOR i ← 1 TO LENGTH(belegung) - 1
    IF belegung[i] > max THEN
        max ← belegung[i]
    END IF
    IF belegung[i] > 80 THEN
        anzahl ← anzahl + 1
    END IF
END FOR
OUTPUT max, anzahl

Schreibtischtest

Du gehst das Skript Zeile für Zeile durch und notierst nach jedem Schritt die Werte der Variablen in einer Tabelle:

Schrittibelegung[i]maxanzahl
Start––00
1. Durchlauf171710
2. Durchlauf265710
3. Durchlauf388881

Ausgegeben werden 88 und 1, richtig wären 92 und 2. Die Tabelle zeigt die Ursache: i beginnt bei 1, das erste Element mit dem Index 0 wird nie angesehen. Korrektur: FOR i ← 0 TO LENGTH(belegung) - 1.

Ein zweiter, versteckter Fehler: max ← 0 klappt nur, solange mindestens ein Wert nicht negativ ist. Sind alle Werte negativ, etwa wenn dasselbe Skript später die Temperaturen des Gefrierschranks für Laborproben mit −18 und −21 auswertet, bleibt max fälschlich 0. Sicherer ist max ← belegung[0], wobei die Liste nicht leer sein darf.

Mit Testdaten prüfen

  • Grenzfälle durchspielen: leere Liste, ein einziges Element, Wert genau auf der Grenze (80 %), größter Wert am Anfang und am Ende (Grenzwertanalyse, LF5, Kapitel 5.6.1).
  • Durchschnitt: In der Schleife summe ← summe + belegung[i], danach durchschnitt ← summe / LENGTH(belegung). Bei leerer Liste entsteht eine Division durch 0, ein Laufzeitfehler.
  • Trockenlauf: Viele PowerShell-Befehle, die etwas ändern, kennen den Parameter -WhatIf. Er zeigt nur an, was passieren würde.
  • Fehler behandeln: Mit try und catch fängt das Skript Fehler ab, protokolliert sie und meldet sich, statt mittendrin abzubrechen. catch greift nur bei Fehlern, die die Ausführung beenden; Cmdlets gibst du dafür -ErrorAction Stop mit.
  • Erst Testumgebung, dann wenige echte Systeme, dann alle (wie beim Patch-Management, Kapitel 10.5.4).

Beispiel

Das Skript zum Anlegen der Konten (Kapitel 10.7.1) prüft die Auszubildende zuerst in einer Test-OU mit einer CSV-Datei mit drei Testpersonen, darunter eine mit einer Rolle, die es nicht gibt. Das Skript meldet einen Fehler; das Konto ist angelegt, steckt aber in keiner Gruppe, und im Protokoll steht nichts davon. Sie ergänzt try und catch (mit -ErrorAction Stop), damit fehlerhafte Zeilen protokolliert werden, und lässt das Skript erst danach auf die echte OU los.

„Bei meinen Testdaten stimmt das Ergebnis, also ist das Skript richtig.“ Der Startindexfehler oben bleibt unbemerkt, solange das erste Element weder der größte Wert ist noch über 80 % liegt. Wähle Testdaten deshalb gezielt so, dass sie Grenzfälle treffen.

  • Schreibtischtest: Skript Zeile für Zeile durchgehen und Variablenwerte je Schritt in einer Tabelle notieren; typische Fehler sind falscher Startindex und ungeeignete Startwerte.
  • Testen mit Grenzfällen, Trockenlauf (-WhatIf), Fehlerbehandlung (try/catch) und erst in der Testumgebung.
