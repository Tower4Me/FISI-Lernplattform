UML-Diagramme AP1

Einstieg

UML ist wie ein genormter Satz an Bauplan-Symbolen, den jede Baufirma versteht, egal wer den Plan gezeichnet hat. Ein Use-Case-Diagramm ist wie ein Grundriss, der zeigt, wer durch welche Tür kommt und was dort erledigt wird (Akteure und ihre Interaktionen). Ein Klassendiagramm ist der Bauplan der Rauminnenstruktur — welche Räume gibt es, wie hängen sie zusammen. Und ein Aktivitätsdiagramm ist der Ablaufplan der tatsächlichen Arbeitsschritte im Gebäude — was passiert zuerst, wo wird entschieden, was läuft parallel.

Konzept

UML (Unified Modeling Language) ist eine genormte, programmiersprachenunabhängige grafische Notation zur Modellierung von Software-Systemen. Sie hilft Entwicklern, Kunden und weiteren Beteiligten, ein gemeinsames Verständnis eines Systems zu entwickeln, bevor programmiert wird.

Sprung zu: Use-Case-Diagramm · Klassendiagramm · Aktivitätsdiagramm · Sequenzdiagramm

Use-Case-Diagramm

Zeigt, welche Akteure (Nutzer, externe Systeme) mit dem System interagieren und welche Anwendungsfälle (Use Cases) dabei genutzt werden. Use Cases können außerdem untereinander in Beziehung stehen — dafür gibt es zwei unterschiedliche, oft verwechselte Beziehungstypen: <<include>> (zwingend) und <<extend>> (optional).

ElementDarstellungBedeutung
AkteurStrichmännchenNutzer oder externes System, das mit dem System interagiert
Use CaseEllipseein konkreter Anwendungsfall/eine Funktion des Systems
SystemgrenzeRechteckgrenzt das modellierte System vom Rest der Welt ab
<<include>>gestrichelter Pfeil, zeigt zum eingebundenen Use Caseder Basis-Use-Case bindet den anderen immer, zwingend mit ein (Pfeil zeigt vom Basis- zum eingebundenen Use Case)
<<extend>>gestrichelter Pfeil, zeigt zum Basis-Use-Caseein Use Case erweitert den Basis-Use-Case nur optional, unter einer Bedingung (Pfeil zeigt vom erweiternden zum Basis-Use-Case — umgekehrte Richtung wie bei include)

Klassendiagramm

Zeigt die statische Struktur eines Systems: Klassen mit ihren Attributen und Methoden sowie Beziehungen zwischen den Klassen. Eine Klasse wird als Rechteck mit drei Bereichen dargestellt: Klassenname, Attribute, Methoden.

BeziehungstypBedeutung
Assoziationallgemeine Verbindung zwischen zwei Klassen
Generalisierung (Vererbung)eine Klasse erbt von einer allgemeineren Klasse (siehe Einheit Programmierparadigmen)
Aggregation„hat-ein“-Beziehung, Teile können auch unabhängig vom Ganzen existieren
Kompositionstarke „hat-ein“-Beziehung, Teile existieren nicht ohne das Ganze

Aktivitätsdiagramm

Zeigt den Ablauf eines Prozesses oder Algorithmus — ähnlich einem klassischen Flussdiagramm, aber als Teil des UML-Standards. Wichtige Elemente: Startknoten, Aktivitäten (abgerundete Rechtecke), Entscheidungsknoten (Raute — entspricht der Verzweigung aus der Einheit Datentypen & Kontrollstrukturen), parallele Abläufe (Balken für Fork/Join) und Endknoten.

Im Unterschied zur Entscheidung (Raute, genau ein Pfad wird durchlaufen) starten Fork/Join-Balken mehrere Pfade gleichzeitig und warten anschließend, bis alle wieder fertig sind:

Sequenzdiagramm

Zeigt, in welcher zeitlichen Reihenfolge Objekte oder Akteure über Nachrichten miteinander kommunizieren — im Gegensatz zum Klassendiagramm (statische Struktur) und zum Aktivitätsdiagramm (Ablauf ohne feste Beteiligte) steht hier der Nachrichtenaustausch zwischen konkreten Teilnehmern im Vordergrund.

ElementDarstellungBedeutung
Lebensliniegestrichelte senkrechte Linie unter einem KopfrechteckExistenz eines Objekts/Akteurs über die Zeit (Zeitachse verläuft von oben nach unten)
Aktivierungsbalkenschmales Rechteck auf der Lebensliniezeigt, wie lange ein Objekt aktiv eine Nachricht verarbeitet
Nachricht/Aufrufdurchgezogener Pfeilein Objekt ruft eine Methode eines anderen Objekts auf
Rückgabe (Antwort)gestrichelter Pfeildas Ergebnis eines Aufrufs geht zurück an den Absender

Praxisbeispiel

Die TechNord GmbH plant eine neue Online-Bestellfunktion und erstellt vor der Programmierung vier UML-Diagramme:

  • Use-Case-Diagramm: Der Akteur „Kunde“ nutzt den Use Case „Bestellung aufgeben“, der wiederum per <<include>> zwingend den Use Case „Zahlung prüfen“ einbindet — und optional per <<extend>> um „Rabattcode einlösen“ erweitert wird, falls der Kunde einen Code besitzt.
  • Klassendiagramm: Die Klassen „Kunde“, „Bestellung“ und „Position“ werden mit ihren jeweiligen Attributen modelliert — eine Bestellung besteht aus mehreren Positionen (Aggregation).
  • Aktivitätsdiagramm für den Bestellprozess: Start → Warenkorb prüfen → Entscheidung „Lagerbestand ausreichend?“ → bei Ja: Zahlung abwickeln, bei Nein: Kunde benachrichtigen → Ende.
  • Sequenzdiagramm für den technischen Ablauf im Hintergrund: Der Kunde ruft „Bestellung aufgeben()“ am Bestellsystem auf, das Bestellsystem fragt beim Zahlungsdienst „pruefeZahlung()“ an und erhält eine Bestätigung zurück, bevor es dem Kunden die Bestellbestätigung meldet.

Alle vier Diagramme entstehen, bevor eine Zeile Code geschrieben wird — sie dienen der gemeinsamen Abstimmung zwischen Entwicklungsteam und Fachabteilung.

Merksatz

UML ist eine genormte, sprachunabhängige Modellierungsnotation. Use-Case-Diagramm = wer (Akteur) nutzt was (Use Case); <<include>> bindet zwingend ein, <<extend>> erweitert nur optional. Klassendiagramm = statische Struktur mit Klassen, Attributen, Methoden und Beziehungen (Assoziation, Generalisierung, Aggregation, Komposition). Aktivitätsdiagramm = Ablauf mit Start/Ende, Aktivitäten, Entscheidungsknoten und parallelen Abläufen. Sequenzdiagramm = zeitliche Reihenfolge von Nachrichten zwischen Objekten über Lebenslinien (durchgezogener Pfeil = Aufruf, gestrichelter Pfeil = Rückgabe).
