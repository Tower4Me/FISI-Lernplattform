Das Projektteam sitzt nicht zusammen: Die Auszubildende arbeitet im Systemhaus, der Kollege an zwei Tagen in der Woche beim Kunden, die Kollegin im Homeoffice. Trotzdem soll jeder wissen, wer gerade woran arbeitet, und keine Änderung soll ungeprüft in den laufenden Betrieb gehen. Dafür braucht das Team gemeinsame Werkzeuge und klare Absprachen.

Ein gemeinsamer Ablauf

  1. Aufgabe anlegen: Jede Aufgabe steht als Ticket (englisch Issue) mit Beschreibung, Verantwortlichem und Status auf einem gemeinsamen Board, etwa einem Kanban-Board (LF5, Kapitel 5.5.1).
  2. Branch anlegen: Für das Ticket entsteht ein eigener Branch (Kapitel 8.5.1).
  3. Änderung zur Prüfung stellen: Ist die Arbeit fertig, stellt die Bearbeiterin einen Pull Request (bei GitLab: Merge Request). Das ist die Bitte, den Branch in main zu übernehmen. Er zeigt alle Änderungen übersichtlich an.
  4. Automatisch prüfen: Continuous Integration (CI) heißt: Änderungen häufig zusammenführen und jedes Mal automatisch bauen und testen. Ein CI-Dienst führt dazu bei jedem Pull Request Tests und Prüfskripte aus. Schlägt ein Test fehl, ist das sofort sichtbar.
  5. Code-Review: Eine zweite Person liest die Änderungen, stellt Fragen und gibt Hinweise. Erst nach ihrer Zustimmung wird zusammengeführt.
  6. Zusammenführen und schließen: Der Branch wird in main übernommen, das Ticket gilt als erledigt.

Ein Code-Review findet Fehler früh und verteilt Wissen: Mindestens zwei Personen kennen jede Änderung. Ein Review ist sachlich und bezieht sich auf den Code, nicht auf die Person; die Regeln für gutes Feedback aus LF1, Kapitel 1.6.3 gelten auch hier.

Bei der Auswahl zählen nicht nur Funktionen: Wo liegen die Daten, braucht es einen Vertrag zur Auftragsverarbeitung (Kapitel 8.1.3), was kostet es je Person, kennen die Beteiligten das Werkzeug schon? Ein selbst betriebener Dienst hält die Daten im Haus, muss aber gewartet und gesichert werden.

Absprachen und Sicherheit

  • Niemand schreibt direkt in main; der Hauptzweig ist im Repository-Dienst geschützt und nimmt nur geprüfte Pull Requests an.
  • Das Team legt fest, wann eine Aufgabe als fertig gilt (Definition of Done, LF5, Kapitel 5.5.1), etwa: getestet, geprüft, dokumentiert.
  • Entscheidungen, die in einem Gespräch fallen, stehen danach im Ticket, damit auch Abwesende sie finden.
  • Zugänge zu Repository und Servern mit Mehr-Faktor-Authentifizierung; der Zugriff auf interne Systeme von außen über VPN.

Beispiel

Die Kollegin im Homeoffice stellt einen Pull Request für den neuen API-Pfad /api/v1/tiere/{id}/impfungen. Die CI meldet einen fehlgeschlagenen Test: Für ein Tier ohne Impfungen kommt Statuscode 500 statt einer leeren Liste. Sie behebt das. Im Review fragt die Auszubildende nach, ob der Dienst prüft, dass das Tier zur angemeldeten Besitzerin gehört (Kapitel 8.4.3). Die Kollegin ergänzt den Test dafür, dann wird zusammengeführt.

„Ein Pull Request ist dasselbe wie git pull.“ Nein: git pull holt die Änderungen der anderen zu dir. Ein Pull Request bittet die anderen, deinen Branch zu übernehmen.

Ein Code-Review lohnt sich nicht nur bei Anfängern. Auch erfahrene Entwickler übersehen Fehler in ihrem eigenen Code. Das Review dient außerdem dazu, dass das Wissen nicht an einer Person hängt.

Ein verteiltes Team arbeitet über Tickets, Branches und Pull Requests. Nichts kommt ohne automatische Tests und Code-Review in main.
