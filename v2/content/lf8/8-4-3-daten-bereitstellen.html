Die Daten liegen jetzt zusammengeführt in der zentralen Datenbank. Nutzen sollen sie ganz verschiedene Empfänger: die Praxisleitung mit ihrem Auswertungsprogramm, das Steuerbüro mit einer monatlichen Liste der Futterkosten und künftig eine App für Terminerinnerungen. Jeder Empfänger bekommt die Daten auf dem Weg, der zu ihm passt, und nur die Daten, die er braucht.

Eine Web-API entwerfen

Wie REST mit Ressourcen, Methoden und Statuscodes arbeitet, kennst du aus LF7, Kapitel 7.3.3. Jetzt bist du auf der anderen Seite und stellst selbst eine Schnittstelle bereit. Für die Termin-App plant die Auszubildende:

GET /api/v1/tiere/31/impfungen
→ 200 OK
[ { "impfstoff": "Tollwut", "datum": "2025-03-04", "faellig": "2026-03-04" },
  { "impfstoff": "Staupe",  "datum": "2025-03-04", "faellig": "2026-03-04" } ]
  • Nur lesen, solange die App nichts ändern muss: nur GET.
  • Anmeldung: Jede Anfrage trägt einen Zugangsschlüssel oder ein Token. Der Dienst prüft bei jeder Anfrage, ob das Tier zur angemeldeten Besitzerin gehört, und antwortet sonst mit einem Fehler (403 oder 404). Sonst könnte man durch Ändern der Nummer im Pfad fremde Daten abrufen.
  • Version im Pfad (v1): Ändert sich die Schnittstelle später, läuft die alte Version weiter, bis alle Apps umgestellt sind.
  • Begrenzung: höchstens eine bestimmte Zahl von Anfragen je Minute, große Ergebnisse seitenweise.
  • Beschreibung: Pfade, Parameter, Antwortformat und Fehlercodes stehen in einer Dokumentation, oft im Format OpenAPI. Danach können andere ohne Rückfrage entwickeln.

Eingaben nie ungeprüft in SQL einbauen

Ein Dienst hinter der API setzt Werte aus der Anfrage in SQL-Abfragen ein, etwa die Tiernummer. Wird der Text der Anfrage einfach in den SQL-Befehl geklebt, kann ein Angreifer eigenen SQL-Code einschleusen. Diese SQL-Injection gehört zu den häufigsten Angriffen auf Webanwendungen.

Gefährlich ist Programmcode wie dieser (vereinfacht), der die Eingabe an den Befehl anhängt:

befehl = "SELECT * FROM impfung WHERE tier_id = " + eingabe

Schickt ein Angreifer als Eingabe 31 OR 1=1, entsteht dieser SQL-Befehl, und weil 1=1 immer zutrifft, liefert er die Impfungen aller Tiere:

SELECT * FROM impfung WHERE tier_id = 31 OR 1=1

Richtig ist eine Abfrage mit Platzhalter, deren Wert getrennt übergeben wird:

SELECT * FROM impfung WHERE tier_id = ?

Bei einer vorbereiteten Abfrage (Prepared Statement) schickt das Programm Befehl und Wert getrennt an das DBMS. Der Wert wird nur als Wert behandelt, nie als Teil des Befehls.

Beispiel

Das Steuerbüro bekommt keinen Zugang zur Datenbank. Ein Skript erzeugt am Monatsersten eine CSV-Datei mit Rechnungsnummer, Datum, Lieferant, Netto- und Bruttobetrag der Futterbestellungen des Vormonats und legt sie verschlüsselt im Austauschordner ab. Die Praxisleitung liest dagegen die Sicht impfungen_je_art mit ihrem Auswertungsprogramm direkt.

„Für die App ist es am einfachsten, die Datenbank ins Internet zu stellen.“ Damit wäre die Datenbank direkt angreifbar, und jede App bräuchte ein Datenbankkonto. Eine API davor nimmt nur festgelegte Anfragen an und gibt nur festgelegte Daten heraus.

Jeder Empfänger bekommt nur eine festgelegte Auswahl: per Datei-Export, Sicht mit Lesekonto oder Web-API. Eine API braucht Anmeldung und vorbereitete Abfragen gegen SQL-Injection.
