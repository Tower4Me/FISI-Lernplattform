Die Web-API der Termin-App (LF9, Kapitel 9.5.4) bekommt eine neue Version. Das Entwicklerteam liefert sie mit dem Satz „Bei mir läuft sie.“ Auf dem Server fehlt dann eine Bibliothek, eine andere hat die falsche Version. Container lösen dieses Problem: Die Anwendung kommt mit allem, was sie braucht, in einem Paket, das überall gleich läuft.

Container und virtuelle Maschine

Ein Container enthält nur die Anwendung und ihre Abhängigkeiten, etwa Bibliotheken und Laufzeitumgebung. Ein eigenes Betriebssystem bringt er nicht mit: Alle Container auf einem Host teilen sich dessen Betriebssystemkern (Kernel). Der Kernel trennt sie voneinander, sodass jeder Container nur seine eigenen Prozesse, Dateien und Netzwerkschnittstellen sieht.

Image, Container, Registry

  • Ein Image ist die unveränderliche Vorlage: Anwendung, Bibliotheken, Einstellungen. Es wird aus einer Bauanleitung erzeugt und mit einem Tag gekennzeichnet, meist der Versionsnummer, etwa termin-api:2.3.
  • Ein Container ist ein laufendes Exemplar eines Images. Aus einem Image können viele gleiche Container starten.
  • Eine Registry speichert und verteilt Images, öffentlich oder im eigenen Betrieb.

Die bekannteste Software dafür ist Docker. Daten, die bleiben sollen, liegen nicht im Container, sondern auf einem eingebundenen Speicherbereich (Volume). So kannst du einen Container jederzeit löschen und durch einen mit neuerem Image ersetzen. Laufen viele Container auf mehreren Hosts, verteilt und überwacht eine Orchestrierung wie Kubernetes sie.

Wann was?

Eine VM wählst du, wenn ein eigenes Betriebssystem nötig ist, etwa für den Verzeichnisdienst oder eine Fachanwendung, die nur unter Windows läuft, oder wenn Kunden oder Bereiche streng voneinander getrennt sein müssen. Container passen zu Anwendungen, die schnell, oft und in vielen gleichen Exemplaren bereitgestellt werden, besonders Webanwendungen. Häufig wird beides kombiniert: Die Container laufen in einer VM.

Beispiel

Das Systemhaus richtet im Stammhaus eine Linux-VM als Container-Host ein. Die Web-API läuft dort als Container aus dem Image termin-api:2.3. Die Termine selbst holt sie aus der zentralen Datenbank; im Volume liegen Konfiguration und Protokolle, die ein Update überstehen müssen. Für das Update auf Version 2.4 lädt die Auszubildende das neue Image, startet einen Container daraus mit demselben Volume und entfernt den alten. Läuft etwas schief, startet sie wieder 2.3; Konfiguration und Protokolle bleiben erhalten.

Weil Container sich den Kernel teilen, kann eine Lücke im Kernel alle Container eines Hosts betreffen. Für Anwendungen mit hohem Schutzbedarf ist eine eigene VM die stärkere Trennung.

  • Container bündeln Anwendung und Abhängigkeiten, teilen sich den Kernel des Hosts, sind klein und starten in Sekunden; VMs haben ein eigenes Betriebssystem und trennen stärker.
  • Image = Vorlage, Container = laufendes Exemplar, dauerhafte Daten gehören in ein Volume.
